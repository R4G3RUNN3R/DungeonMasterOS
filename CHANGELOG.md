# Changelog

## 2026-08-18 (Phase 6)
- In-game UI redesign: implemented Phase 6 (encumbrance/item integration) of the immersive live-play shell on `feature/immersive-ingame-ui-redesign`, per design spec §16 — the final phase of the redesign's original phased sequence.
- **Scope note:** the design spec gated this phase on "reconciling with the master item compendium/inventory work." That branch (`feature/master-item-compendium`) turned out to be a public, read-only item catalogue/browsing UI (cover flow, provenance, source links) — not a character-inventory/weight/carrying-capacity backend. Neither branch had any weight, container, or carrying-capacity data model, so this phase is new backend work rather than a merge, per explicit user decision after the gap was surfaced.
- `items` table: added `weight` (real, lbs per unit) and `carried` (bool, default true) columns. `carried` distinguishes items physically on the character from owned-but-stored assets (spec §16's carried-vs-owned requirement) — a house, a wagon, gear left at the guild hall — which correctly don't count toward carry weight.
- `shared/encumbrance.ts` (new): the real D&D 3.5e SRD Table 9-1 carrying-capacity-by-Strength lookup (exact for Str 1-20, approximated above via the standard "doubles every +10 Str" rule), a documented simplified level-derived fallback for characters with no recorded Strength score, tier classification (light/medium/heavy/overloaded), and the standard 3.5e load penalties (speed reduction, max Dex bonus cap, check penalty) per tier — mirroring the honest-fallback precedent set by Phase 4's combat-engine.ts.
- `client/src/lib/rulesAdapters/dnd35.ts`: the HUD's Carry Weight slot (spec §4.2/§16) has existed since Phase 1 as a hard-coded `null` — real data was explicitly deferred to this phase. Now derives Strength from `characterData.dnd35Sheet.abilities.str.score` when present, else the level-derived fallback, and computes real current/max/tier from the character's actual carried items.
- `CharacterHud.tsx`: the Carry stat now tints amber at heavy load and red at overloaded, matching the existing HP-bar color-by-threshold pattern.
- `InventoryOverlay.tsx`: each item shows its real per-unit weight; a capacity summary bar (current/max + tier label, tier-colored) sits in the header; stored (carried=false) items render muted with a "Stored" badge; a small Carry/Store toggle per item calls the real PATCH endpoint.
- `server/routes.ts`: item create/update routes accept `weight`/`carried`. The AI item-grant extractor (`extractItemsFromNarration`) now asks for a realistic per-unit weight, with a sane per-itemType fallback table if the AI omits one or returns something invalid — property/vehicles/mounts/creatures/retainers are correctly weightless (not carried).
- Deferred, honestly: container and Bag-of-Holding-specific capacity logic — spec §16 explicitly calls this out as needing its own separate logic rather than folding it into base encumbrance, so it wasn't built here.
- Verification: typecheck/build pass clean. Live-verified end-to-end through the real API (registered a user, created a campaign and a level-5 Fighter with a real Strength 16 in the 3.5e sheet, created items via the real item-creation endpoint): HUD showed "CARRY 78/230" (78 = 8+30+40 lbs of carried gear, correctly excluding a 12lb stored item; 230 = the real STR-16 heavy-load threshold from the SRD table), Inventory overlay showed the same 78/230 · Medium Load summary with correct per-item weights and a Stored badge on the excluded item. Clicked the Carry toggle on the stored item — both the HUD and overlay updated to 90/230 in real time via the real PATCH endpoint and its existing `items_updated` WebSocket broadcast. Added a 200lb item to push total to 290/230 and confirmed the tier flipped to "Overloaded" with `getComputedStyle` confirming the HUD stat actually rendered in the danger-red color (not just the right CSS class name).
- Risk: low-to-moderate. New columns are additive (`addColumnIfMissing`, safe on existing databases); the carrying-capacity math is isolated in a pure, unit-testable module; the HUD/Inventory changes only populate a slot that was always rendering "—" before, so there's no working behavior to regress.

## 2026-08-18 (Phase 4)
- In-game UI redesign: implemented Phase 4 (combat UX) of the immersive live-play shell on `feature/immersive-ingame-ui-redesign`, per design spec §10, with the scope explicitly upgraded from a cosmetic-only stub to a real working combat backend per user decision — this branch had zero combat mechanics (no encounters, no combatants, no attack resolution) before this phase.
- **Scope boundary (intentional, documented in-file):** this branch's `characters` table has no ability scores, AC, or BAB — only name/race/class/level/hp/speed/attacksPerRound. Rather than porting the full 3.5e mechanical substrate, `server/combat-engine.ts` uses simplified level-derived defaults (`defaultAttackBonusForLevel`, `defaultArmorClassForLevel`) so combat is real and playable today without silently pretending to be canonical 3.5e math it isn't.
- Schema: new `encounters` and `combatants` tables (`shared/schema.ts`, migrated via `runMigrations()` in `server/storage.ts` following the existing raw-SQL `CREATE TABLE IF NOT EXISTS` pattern) plus matching `IStorage`/`DatabaseStorage` methods.
- `server/combat-engine.ts` (new): d20 attack resolution with crit-on-20/fumble-on-1, damage dice parsing, level-derived stat defaults.
- `server/dm-engine.ts`: DM system prompt now documents `[COMBAT_START]{...}[/COMBAT_START]` and `[SURRENDER]{"name":"..."}[/SURRENDER]` output formats, explicit that the AI proposes combat/surrender but never decides hit, damage, or outcome — the server resolves every roll. Added `narrateCombatResult()` to have the AI narrate an already-decided mechanical result, with a graceful fallback to a plain mechanical summary if the AI call fails.
- `server/routes.ts`: combat orchestration — `startEncounterIfProposed`, `applySurrenderIfProposed`, `advanceCombatTurns` (auto-resolves NPC turns in a guarded loop until it's a player's turn or the encounter ends), `checkEncounterEndReason`. New endpoints: `GET /api/campaigns/:id/encounter`, `POST /api/campaigns/:id/combat/attack`, `POST /api/campaigns/:id/combat/flee` (all turn-limited and gated the same way as the main action endpoint).
- Client: `CombatContext.tsx` (round/turn-order/HP-bar Context Panel view), `ContextActionDeck.tsx` extended with dynamic per-target Attack buttons + Flee, `ContextPanel.tsx` gives Combat top priority over Merchant/Loot/Exploration per spec §8.3, `campaign.tsx`/`CampaignGameShell.tsx` wired to the new encounter query, attack/flee mutations, and `combat_started`/`combat_updated`/`combat_ended` WebSocket events.
- **Bug fix (found during live verification):** `checkEncounterEndReason()` treated "all players fled" and "all players defeated" identically (both reported `"defeat"`). Fixed to check `isDefeated` specifically so `endReason` is semantically correct for any future feature (achievements, campaign history) that reads it — not yet surfaced in the UI itself.
- Verification: since this dev environment has no `ANTHROPIC_API_KEY`, the AI-triggered `[COMBAT_START]` path couldn't fire naturally. Verified the entire real server stack end-to-end instead by seeding a genuine encounter + combatants directly into the running dev server's SQLite database, then exercising it live in the browser: Context Panel correctly showed round/turn/HP bars, dynamic Attack buttons per live NPC, a real server-resolved miss (`d20 roll 10 + attack bonus 1 = 11 vs AC 13 → MISS`), the NPC turn loop auto-resolving two real hits with correct damage, HP syncing correctly across the HUD and Context Panel, and Flee correctly ending the encounter and reverting to Exploration. Typecheck and build both clean (only the two pre-existing unrelated baseline errors present throughout this whole branch).
- Risk: moderate. This is genuinely new server-authoritative game logic (not just a visual pass) — mitigated by keeping the mechanical model honestly simplified/documented rather than inventing unverified 3.5e math, and by the live seeded-encounter verification exercising the real turn-loop, dice resolution, and WebSocket sync rather than just checking that components render.

- **Bug fix (pre-existing, found via hands-on verification, not just eyeballing text):** every Dialog-based overlay since Phase 1 (Inventory, Codex, Character Profile, Shop) has been rendering with the wrong background. `game-shell.css`'s surface utilities were written as `.dm-shell .dm-x` (descendant selector), which only matches when `dm-shell` is an ancestor. Radix Dialogs render through a Portal, breaking real DOM ancestry, so every overlay applies `dm-shell` and a surface class to the *same* element — a pattern the descendant selector can never match. The lower-specificity but actually-matching `bg-background` (shadcn's default) was winning by default the entire time. Fixed by adding compound (`.dm-shell.dm-x`, no space) rules alongside the existing descendant ones in `game-shell.css`, covering both the nested-shell case and the portaled-dialog case. Verified via `getComputedStyle` (not just visible text) on all four affected overlays post-fix.
- Verification: typecheck/build pass clean. Browser-verified end-to-end: opened Codex, Inventory, and Character Profile with real character data, confirmed correct background colors via computed styles (not just DOM text), confirmed the character sheet's bronze header gradient renders. Shop chrome could not be live-triggered (no `ANTHROPIC_API_KEY` to have the DM open a shop) but received the same CSS fix verified working on the other three overlays.
- Risk: low-to-moderate. The CSS specificity fix touches shared utility classes used across the whole redesign — verified it doesn't regress the main shell's own (correctly-nested, already-working) usage of the same classes.
